# UEFI Deployment Notes

These notes define the initial deployment workflow for Yocto Chromebook POC images on Chromebooks already converted to MrChromebox UEFI Full ROM firmware.

This document is not a hardware qualification record. Successful boot evidence, board logs, storage device names, and component status must be captured separately in the hardware matrix and hardware notes.

## Bootloader approach

The POC uses the existing generic x86-64 Yocto UEFI boot path inherited from Poky's `genericx86-64` machine baseline.

Initial boot policy:

- GPT disk image.
- EFI System Partition generated by Yocto/WIC.
- UEFI bootloader contents generated by the selected upstream x86-64 Yocto boot path.
- Root filesystem in the generated WIC image.
- External USB boot first; internal eMMC writes only after the USB path reaches a login shell and storage identity is confirmed.

The project deliberately does not define a custom bootloader stack until the generic x86-64 UEFI path is build- and boot-qualified on target hardware. If the generic path fails, later work should record the exact firmware behavior and then choose a custom WKS/bootloader configuration with evidence.

## Expected image artifacts

A successful POC build is expected to produce WIC artifacts under Yocto deploy output, typically in a machine-specific directory below:

```text
build/tmp/deploy/images/<machine>/
```

Expected artifact classes:

```text
yocto-chromebook-poc-<machine>.wic
yocto-chromebook-poc-<machine>.wic.gz
```

Exact filenames may include timestamps or symlinks depending on Yocto configuration. Testers should use the final WIC or compressed WIC artifact produced by the successful build.

## External USB boot workflow

Use an external USB device for the first boot attempt.

1. Build the desired POC image, for example:

   ```bash
   kas build kas/snappy-poc.yml
   ```

2. Identify the removable USB block device on the build host:

   ```bash
   lsblk -o NAME,SIZE,MODEL,TRAN,TYPE,MOUNTPOINTS
   ```

3. Unmount any mounted partitions from the selected USB device.

4. Write the WIC image to the entire USB device, not to a partition:

   ```bash
   sudo dd if=yocto-chromebook-poc-snappy.wic of=/dev/sdX bs=4M status=progress conv=fsync
   ```

   Replace `/dev/sdX` with the actual USB device. Do not use a partition such as `/dev/sdX1`.

5. Flush writes and remove the USB device:

   ```bash
   sync
   ```

6. Insert the USB device into the MrChromebox UEFI-converted Chromebook.

7. Use the firmware boot menu to select the USB device.

8. Record whether UEFI discovers the device, which boot entry appears, and the first visible kernel or bootloader output.

## Internal eMMC deployment workflow

Internal eMMC deployment is intentionally gated behind successful USB boot evidence.

Before writing to eMMC:

- confirm the board identity;
- confirm that the POC image reaches a shell login from USB;
- record `lsblk`, `blkid`, and kernel storage logs;
- identify the internal eMMC device name;
- confirm the target disk is not the USB boot device;
- preserve any required data manually; and
- require an explicit destructive-write confirmation in any future installer script.

A manual internal write, once qualified, should follow the same whole-device WIC write model as USB deployment, using the confirmed eMMC block device.

## Recovery notes

Keep a known-good recovery path available before internal writes:

- an external USB boot image known to reach a shell;
- MrChromebox firmware recovery knowledge for the specific device;
- another machine capable of rewriting USB media; and
- any original firmware or OS recovery artifacts the tester needs.

## Evidence to capture

For each boot attempt, record:

- board and device model;
- firmware type and version when visible;
- image artifact name and build commit;
- USB device model used for boot;
- UEFI boot menu behavior;
- first bootloader output;
- first kernel log lines;
- whether a login shell is reached;
- `dmesg` excerpts for storage, input, Wi-Fi, Bluetooth, graphics, and audio; and
- any failure text or screenshots.
