# Storage and Update Design

This document defines the initial persistent data, partitioning, deployment, and future update design for `yocto-chromebook`.

The first POC remains a build and boot validation target. Production-grade A/B updates are deliberately documented now so early POC partition choices do not block that direction later.

## Design goals

- Keep the OS image replaceable.
- Keep user data and optional user applications persistent across rootfs replacement.
- Avoid an end-user package manager as the primary application model.
- Make destructive disk operations explicit and hard to trigger accidentally.
- Preserve room for future A/B rootfs updates on 16 GB eMMC devices.

## Initial POC partition layout

The first POC image uses the generic Yocto x86-64 UEFI WIC image path inherited from the current machine baseline.

Initial layout policy:

```text
GPT disk
├── EFI System Partition
└── rootfs
```

For POC-1, `/data` may be represented as a directory on the writable rootfs if a separate data partition is not yet generated by the WIC image. This keeps the first image simple while preserving the application/data path convention that later partition work will make persistent across OS replacement.

The generated image must still remain compatible with a later split layout because no user-facing policy should depend on storing data inside system-owned directories.

## Future persistent layout

The intended production layout is:

```text
GPT disk
├── EFI System Partition        128 MiB target
├── rootfs-A                    512 MiB to 1024 MiB target
├── rootfs-B                    512 MiB to 1024 MiB target
└── data                        remaining space
```

The exact rootfs sizing should be set after measured POC and desktop image sizes exist. The targets above are design placeholders, not hard gates.

## `/data` layout

`/data` is the persistent ownership boundary between the OS image and user/application state.

Target layout:

```text
/data/
├── apps/
├── home/
├── downloads/
├── config/
└── logs/
```

Path policy:

- `/data/apps` stores optional AppImages and their launcher metadata.
- `/data/home` is the future persistent user-home backing store.
- `/data/downloads` is the default large-download staging area.
- `/data/config` stores persistent machine-local or user-local configuration that should survive rootfs replacement.
- `/data/logs` stores opt-in diagnostic logs copied out of the system journal or hardware validation scripts.

## `/home` policy

The preferred production direction is a bind mount or equivalent persistent mapping from `/data/home` to `/home`, not an ad hoc symlink created by a user after install.

For early POC work:

- `/home` may remain in the rootfs while boot and package baseline work is still being qualified.
- Tests and documentation should refer to `/data/home` as the persistence target.
- Any migration from rootfs `/home` to `/data/home` must preserve ownership, permissions, and dotfiles.

## AppImage storage policy

Optional user applications are stored under `/data/apps`.

A later AppImage installer/registrar can:

1. copy or move an AppImage to `/data/apps`;
2. mark it executable;
3. extract icon and desktop metadata when available;
4. create launcher entries; and
5. keep the application file and user state outside the rootfs.

Unsupported AppImages should fail with captured logs rather than being copied into system-owned directories.

## Backup implications

A user-data backup should include at least:

```text
/data/home
/data/apps
/data/downloads
/data/config
```

`/data/logs` may be excluded from routine backups unless the user is preserving validation evidence.

Rootfs partitions are not the canonical backup target. They should be reproducible from build artifacts.

## Manual installer decision

POC-1 does not require a custom installer script. The documented process is a manual WIC whole-device write with explicit target-device confirmation.

A future installer script is appropriate only after the USB boot path and eMMC device identity are qualified on target hardware.

Any future installer must implement at least these safety checks:

- print all candidate block devices with model, size, transport, and mounted filesystems;
- reject mounted target partitions unless the user explicitly unmounts them;
- reject the currently booted source disk;
- require typing the exact target device path;
- display a destructive-write warning immediately before writing;
- preserve `/data` when doing an OS-slot update rather than a fresh install; and
- capture an install log under `/data/logs` when `/data` exists.

## Future A/B update design

A/B updates are not required for POC-1, but the production update direction is:

```text
running rootfs-A
    -> write new rootfs image to rootfs-B
    -> verify image hash/signature
    -> mark B as the next boot target
    -> reboot
    -> confirm boot health
    -> keep A as rollback until B is accepted
```

### Boot-state mechanism

The boot-state mechanism should be selected during the production-update milestone. Acceptable candidates include:

- UEFI boot variables with explicit rootfs labels or partition UUIDs;
- bootloader environment state if the selected bootloader supports it safely; or
- an existing Yocto update framework that already integrates boot-state and rollback.

The choice must be validated on MrChromebox UEFI hardware before being considered supported.

### Update artifact format

The expected production update artifact is a whole rootfs image plus metadata:

```text
rootfs image
metadata manifest
hashes
signature or verification data
compatibility information
rollback/boot-state instructions
```

The full-disk WIC image remains useful for fresh installs, recovery media, and POC validation. Routine production updates should not overwrite `/data`.

### Verification mechanism

The production updater should verify:

- artifact hash before writing;
- signature or trust policy before activation;
- target board compatibility;
- target slot identity;
- successful write and sync;
- bootloader state update; and
- post-boot health marker before accepting the new slot.

### Rollback behavior

Rollback policy:

- never overwrite the currently booted known-good slot during a normal update;
- mark the new slot tentative until the system confirms a successful boot;
- keep a bounded retry count;
- revert to the previous slot if the tentative slot fails; and
- preserve `/data` across both success and rollback.

## Relationship to POC-1

POC-1 may ship with a simpler single-rootfs WIC layout. That is acceptable as long as:

- user-facing paths already use `/data` conventions;
- deployment docs warn that internal writes are destructive;
- the POC does not hard-code assumptions that prevent a later data partition; and
- the TODO keeps hardware validation distinct from the update design.
